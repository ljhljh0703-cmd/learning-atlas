# 설명은 결정권자에게 하듯 한다

> 🔒 **작가 지시 2026-08-24.** 이건 문체 취향이 아니라 **작업 요건**이다.
> 작가가 "무슨 말인지 모르겠다"고 하면 **그 설명은 실패다.** 내용이 맞았는지는 상관없다.

## 사고 기록 (이 규칙이 생긴 이유)

문학 카드 스키마 확장 건에서, 작가가 결정해야 할 사항을 설명하라는 요청에
`conflict_axis`·`new_field_gate`·`K4 항등식`·`절대룰 #7`·`P-1~P-5`·`FIELD_AMEND` 를 주어로 써서 설명했다.
전부 내부 용어였고, 작가는 "하나도 모르겠다"고 답했다.

**원인**: 나는 내가 아는 구조를 순서대로 늘어놨고, **작가가 무엇을 결정해야 하는지**를 먼저 세우지 않았다.
정확했지만 쓸모가 없었다. 결정권자는 시스템 내부를 몰라도 결정할 수 있어야 한다.

**재발 2026-08-27 (recurrence 2).** Codex 패킷 게이트 결과를 보고하면서 `③Gate`·`dedup`·`SELECTIVE MERGE`·`review_trigger`·`load-bearing` 을 주어로 쓴 표 두 장을 냈다.
작가: *"그래서 본론이 뭔데. 알기 쉽게 설명하라고 500번 말했다."*
**원인이 08-24 와 다르다** — 그때는 순서를 안 세웠고, 이번엔 순서는 세웠으나 **검증 과정을 성과로 착각해 전부 보여줬다.** 게이트를 얼마나 꼼꼼히 돌렸는지는 내 관심사이지 결정 재료가 아니다. §6(화면 한 장)이 이미 막았어야 했는데, 표는 접은 것처럼 보여서 자가점검을 통과해버렸다. → 자가점검에 「표도 분량이다」 추가.

## 규칙

### 1. 순서를 고정한다

1. **뭘 만들고 있나** — 한 문장. 비유 허용
2. **뭐가 문제인가** — 한 문장
3. **당신이 정할 것** — 번호 붙여 나열
4. **안 정하면 뭐가 막히나** — 실제로 막히는 것만
5. (부록) 근거·파일 경로·규칙 번호

### 2. 내부 용어를 설명의 주어로 쓰지 않는다

| 쓰지 않는다 | 대신 |
|---|---|
| `conflict_axis` 필드 신설 | 갈등을 적는 칸을 만든다 |
| `card_fields_total: 18` → 19 | 카드 항목이 18개에서 19개가 된다 |
| 48칸 미충전 | 빈칸 48개를 채워야 한다 |
| 절대룰 #7 위반 | 내가 만든 걸 내가 승인하는 셈이라 안 된다 |
| `SKIP_RED` | 검사를 못 했으면 통과가 아니다 |
| P-1 권리 레인 미판정 | 이 작품을 분석해도 되는지 아직 확인 안 됐다 |

용어를 **쓸 수는 있다.** 단 괄호로 뒤에 붙이지, 문장의 주어로 쓰지 않는다.

### 3. 비용은 작가가 세는 단위로 숫자를 댄다

"K4 연동 교정 필요" ❌ → "칸 하나 만들 때마다 채울 빈칸이 634개 생긴다" ✅
막연한 형용사(무겁다·부담된다·비용이 크다) 금지. **숫자 아니면 시간.**

### 4. 선택지마다 추천 1개 + 이유 1줄

"작가 결정 항목입니다"로 끝내지 않는다. 그건 판단을 미루는 것이지 존중이 아니다.
**추천을 대고 이유를 한 줄로 댄다.** 그리고 그게 추천일 뿐임을 명시한다.

### 5. 진짜 병목을 먼저 말한다

선택지를 다 정해도 일이 안 굴러가면, **그 사실을 선택지보다 먼저** 말한다.
결정권자가 엉뚱한 데 시간을 쓰게 두는 것이 가장 큰 손실이다.

### 6. 길이

**결정 설명은 화면 한 장.** 넘어가면 표로 접거나 부록으로 내린다.
근거를 다 보여주고 싶은 충동은 내 불안이지 작가의 필요가 아니다.

### 7. 한 번에 하나만 낸다 <!-- 흡수 2026-08-27 paperthin(hate·feynman·readchk 3개가 독립적으로 같은 규칙에 도달) · proposed_by: claude(외부 해체) · confirmed_by: user 2026-08-27 -->

갈래가 여럿이면 **가장 값비싼 것 하나만** 내놓는다. 나머지는 그게 풀린 다음이다.
체크리스트로 묶어 내는 건 정리처럼 보이지만 실제로는 **판단을 작가에게 통째로 떠넘기는 것**이다.

- 반론을 낼 때 = 계획을 무너뜨리는 **단 하나의 반론**과, 그게 진짜인지 밝힐 **가장 싼 검사** 하나. 목록 금지.
- 되물을 때 = 미해결 갈래 하나. 여러 개면 손해 큰 것부터.
- 같은 질문을 반복하지 않는다. 답이 얕으면 **더 좁혀서** 묻는다. 두 번째로 같은 질문을 하면 작가는 더 크게 말할 뿐이고, 좁힌 질문만이 갈래가 실제로 닫혔는지 시험한다.

### 8. 지시는 되뇌지 말고 다른 말로 옮겨본다 <!-- 흡수 2026-08-27 paperthin/readchk -->

긴 지시·묶음 지시·되돌리기 힘든 작업·「이거/그거/저번 거」 같은 대명사가 있으면, 착수 전에 **내 말로 바꿔** 적어본다. 작가 문장을 그대로 복창하는 건 이해의 증거가 아니다.

- 맥락이 갈래를 풀어주면 **조용히 진행한다.** 이미 답이 있는 걸 되묻는 건 결함이다.
- 진짜 갈래가 남으면 **그 갈래를 이름 붙여** 묻는다. "이거 맞나요?" 는 질문이 아니다.
- 큰 작업(계획·다중 파일 수정·되돌리기 어려운 실행)은 시작 전에 **「이렇게 이해했다: …」 한 줄**을 남긴다. 나중에 산출물이 그 이해와 맞는지 대조할 수 있어야 한다.

### 9. 자료가 두껍고 요청이 얇으면, 묻지 말고 제안한다 <!-- 흡수 2026-08-27 paperthin/aim -->

파일 뭉치·레포·긴 붙여넣기가 들어왔는데 요청이 한 줄이면, **"뭘 원하세요?"를 되묻지 않는다.**
전부 읽고 → **읽힌 의도 한 줄** + **다음 행동 한 줄**을 제안하고 → **맞음 / 고침 / 아님** 셋 중 하나만 받는다.
단 자료가 너무 얇아 추측이 되는 지점에서는 제안하지 말고 멈춘다.

## 자가 점검 (설명 보내기 전)

- [ ] 첫 세 문장 안에 "당신이 정할 것"이 나오는가
- [ ] 내부 용어가 **문장의 주어**로 쓰인 곳이 있는가
- [ ] 선택지마다 숫자 비용과 추천이 붙었는가
- [ ] 다 정해도 안 굴러가는 게 있으면 그걸 먼저 말했는가
- [ ] 화면 한 장인가 — **표도 분량이다**(접은 것처럼 보일 뿐)
- [ ] 내가 얼마나 꼼꼼히 했는지를 설명에 넣지 않았는가 (검증 과정 ≠ 결정 재료)
- [ ] 물어볼 게 여럿이면 **하나만** 냈는가
