# 한글 리터럴 I/O 하네스 (오타 재발방지)

> **한 줄**: 도구 인자에 한글을 `\uXXXX` 이스케이프로 넣지 마라. 항상 리터럴 UTF-8 한글로. 편집 후 grep으로 확인.

## 근본 원인 (2026-07-20 관측)

망원동/스킬 작업 중 한글 편집에서 오타가 반복됨: 즙불가지(→불가지)·뛴(→결)·어깴다(→어긋난다)·진지(→진짜)·퍼즘(→퍼즐)·휘다(→휜다)·열어둘(→열어둠)·캐(→캔)·뭐모른(→뭘 모른)·몫/몸/얌/얀/얘 혼동·앨남김/얀전함/얘전함(→얌전함).

- **원인 = 인코딩 산수 오류.** `edit_file`·`AskUserQuestion` 등 도구 인자에 한글을 `\uXXXX`로 수기 인코딩했음. 한글 음절은 조합 공식 `0xAC00 + ((초성×21)+중성)×28 + 종성`으로 계산되는데, 이 오프셋을 손으로 계산하다 **인접한 유효 음절**로 빗나감. 맞춤법 지식 문제가 아니라 코드포인트 계산 문제.
- **증거**: `write_file`로 리터럴 한글을 쓴 스킬 본문·채팅 산문은 전부 FFFD 0·오타 0. 틀린 글자는 **전부** `\u` 이스케이프 편집 자리에서만 발생.
- **2차 원인**: `edit_file` oldText를 기억으로 재입력(캔→캐, 뭘→뭐) → 매칭 실패·원자적 롤백 churn.

## 하네스 규칙 (비협상)

- **H1 (핵심)**: 한글은 도구 인자(edit_file·write_file·AskUserQuestion·SendUserMessage 등)에 **항상 리터럴 UTF-8 한글로 직접 입력**. `\uXXXX` 수기 인코딩 **영구 금지**.
- **H2**: `edit_file` oldText는 **재입력 금지**. 직전 `Read`/`Grep` 출력에서 대상 문자열을 **정확히 복사**해 붙인다.
- **H3**: 한글 파일 편집 직후 **grep 스팟체크** — ① FFFD(U+FFFD) 카운트 0 확인 ② 방금 넣은 의심 어휘가 실제로 존재하는지 grep.
- **H4**: SSOT·스킬·발송물(디스패치·이메일)의 확정 라인은 편집 후 **grep 재확인 게이트** 통과 후 완료 처리.

## 참고

- read_text_file / device_bash 출력에 보이는 한글 깨짐(FFFD 표시)은 **표시 아티팩트**일 수 있음 — 파일 바이트는 멀쩡한 경우 많음. 진위 판정은 `grep -c $'\xef\xbf\xbd'`(실제 바이트) 기준.
- 정본 관련: lessons · 오타 게이트는 모든 한글 산출의 기본 절차로 편입.

## H5 — 기존 대용량 파일에 write_file 금지 (2026-07-20 사고)

**사고**: log.md(897줄 이력)에 `write_file`로 상단 엔트리만 재작성하려다 하단 844줄 커밋 이력 + 오늘 미커밋 엔트리 일부를 truncate. git HEAD로 복구했으나 미커밋분 일부는 요지 재구성.

- **H5**: 기존 파일에 내용을 **추가·수정할 땐 `edit_file`(append/prepend)만.** 존재하는 파일에 `write_file`(전체 덮어쓰기) 금지 — 특히 로그·SSOT처럼 append-only 이력 파일. write_file은 **신규 파일 생성 전용**.
- **H6**: 대용량/이력 파일 편집 후 **줄수·프론트매터 개수 대조**(편집 전후 wc -l, `grep -c "^---$"`=2). 급감 시 즉시 git 복구(`git show HEAD:<path>`).
