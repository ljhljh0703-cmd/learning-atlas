# Hackathon Judgeability Gate (v0)

> ⚠️ **임시 — 파일럿 0회.** AX 인재전쟁 1기 운영팀 **전체 심사 집계**에서 도출했으나, 실제 대회에서 아직 한 번도 돌려보지 않았다. 대회별 공식 루브릭이 항상 이 Gate보다 우선한다. 수상 예측 도구가 아니다.

**목적**: "좋은 아이디어 + 많은 구현"을 `문제 → 근거 → 가설 → 동작 → 비즈니스 결과 → 전달`의 **증거 사슬**로 바꾼다.

**짝 노드**: [AX 해커톤 승리 플레이북 (우승자 2인 수렴)](ax-hackathon-winning-playbook.md)(우승자 2인 — 프레이밍·신뢰·전달) · [Re:Cart 해체 — "머리 vs 손" 결정 계층 + 승리 요인 해부](../techniques/recart-decision-layer-teardown.md)(결정론·판매자 경제성 인스턴스). 이 Gate는 *운영 계약*, 플레이북은 *승리 패턴* — 역할이 다르므로 합치지 않는다.

## 왜 이게 필요한가 (집계가 말한 것)

예선 약 5,300명 → 자격 통과 1,277건 → 본선 60명(약 88:1). 갈린 지점은 참신함이 아니었다.

| 축 | 집계 (organizer_reported) |
|---|---|
| 문서↔실물 일치 | 끝까지 작동 41.7% · 절반 54.0% · 사실상 비작동 4.4% |
| 출처 유효성 | 인용 3건 중 1건이 없거나 주장과 무관 — **본선 진출/근접 탈락 차이가 가장 컸던 축** |
| 판정 사유 최빈어 | `병목` 2,391회 |
| 정직성 | 정직 1,657 · 한계 1,339 · 실패 1,011 — 본선 진출자 최고 평균 축 |
| 재현 증거 | 증거 2,185 · 구체 1,849 · 실행 1,260 |
| AI 활용 | **상위권과 나머지 차이가 가장 작음** — 변별력은 활용량이 아니라 통제 가능성 |

핵심: **AI를 썼다는 사실은 이미 기본 위생이다.** 핵심 판정을 실행 시점 LLM에 맡긴 설계는 "통제 부재"로 읽힌다.

## 상태어 (서로 대체 불가)

| 상태 | 뜻 |
|---|---|
| `IDEA_BLOCKED` | 문제·근거·가설 중 하나가 없어 구현하면 안 됨 |
| `PLAN_READY` | 문제·근거·가설·비즈니스 결과가 잠김 |
| `SLICE_READY` | 한 개 end-to-end slice가 가설을 증명함 |
| `SUBMISSION_READY` | clean run·claim parity·출처·한계·패키지가 닫힘 |
| `PITCH_READY` | 실제 제한 시간 안에서 데모·비즈니스·Q&A까지 재현됨 |
| `RESULT_PENDING` / `AWARD_CONFIRMED` | 제출 완료 / 공식 수상 확인 |

`Tests PASS` ≠ `SUBMISSION_READY` ≠ `PITCH_READY` ≠ `AWARD_CONFIRMED`.

## 철칙 (비보상형)

> **판정 가능한 증거 없이 구현 없음.**

가중 총점으로 약점을 덮지 않는다. 아래 blocker가 **하나라도** 있으면 다음 단계로 가지 않는다.

- 핵심 문제의 존재·빈도·비용 근거 없음
- 한 문장 병목 정의 없음
- 핵심 가설을 증명하지 않는 데모
- README·발표 주장과 실제 동작 불일치
- 핵심 인용이 없거나 주장과 무관
- 판정·계산을 실행 시점 LLM에 맡기고 변동성을 통제하지 않음
- fresh environment에서 실행 불가
- 비즈니스 결과가 vanity metric(조회·노출)에 멈춤
- 실제 제한 시간 발표를 끝까지 재현하지 못함
- 만든 로직을 본인이 설명하지 못함

## Gate 0 — Challenge Truth Lock (구현 전)

공고·문제·평가 기준·제출 폼·분량·시간 제한을 **직접** 확인 / sponsor 기존 제품·공식 용어 확인 / 이미 있는 기능과 우리가 메울 빈틈 구분 / 필수 API·데이터·권한 조건 확인 / 제출 형식·공개 범위·라이선스·개인정보 조건 확인.
증거 = authority URL·snapshot · 확인 시각 · 변경 가능 항목 · unknown 목록. **실패 시 `IDEA_BLOCKED`.**

## Gate 1 — Problem Admission

한 문장을 한 번에 채운다.

> `[사용자/담당자]`가 `[구체 상황]`에서 `[현재 방법의 실패]` 때문에 `[시간·비용·위험·기회 손실]`을 겪는다.

- 사용자·상황이 실명 가능한 수준으로 구체적인가
- **"API 연동"·"AI 추천"·"플랫폼 구축"은 할 일이지 병목이 아니다**
- 현재 방법이 *왜* 실패하는지 설명되는가 / 실제 발생 근거가 있는가
- 직접 경험이 없으면 그 대체 증거와 한계를 명시했는가
- sponsor 기존 제품을 복제하지 않고 빈틈을 메우는가

**실패 시 구현 금지 — 문제 정의로 복귀.**

## Gate 2 — Evidence Admission

핵심 주장마다 ledger를 만든다.

| claim | source | status | literal anchor | design consequence |
|---|---|---|---|---|
| 이 문제가 존재·반복한다 | 공식 문서·공시·로그·인터뷰 | verified / organizer_reported / user_reported / assumed / unknown | 원문 근거 | 그래서 무엇을 설계했나 |

**URL이 열리는 것과 주장을 지지하는 것은 별도 확인한다.** 출처 때문에 달라진 설계 결정이 적혀 있어야 한다. 일반론·검색 요약·출처 없는 AI 생성 수치를 핵심 근거로 쓰지 않는다. 충돌 근거를 숨기지 않는다.
**통과 기준: 핵심 주장 source-to-design closure 100%.**

## Gate 3 — Causal Product Contract

> `문제 → 관측 신호 → 메커니즘 → 행동 → 사용자 변화 → 비즈니스 결과`

각 화살표에 관측 가능한 입력 · 실패 가능한 가정 · 검증 방법 · 대안/기준선을 붙인다.
데모 장면 **하나**가 이 사슬 전체를 보여줄 수 있어야 한다. 결과 지표는 조회·노출을 넘어 전환·매출·비용·회수·위험·처리시간 중 하나에 연결된다. 수치가 없으면 `미정 — 검증 필요`로 표시한다. **실패 시 `PLAN_READY` 금지.**

## Gate 4 — AI Control Boundary

| 역할 | 담당 |
|---|---|
| 애매한 언어·패턴 해석 | AI 가능 |
| 판정 기준·계산·정책·한도 | **결정론 코드 우선** |
| 위험·비가역 행동 | 인간 승인 또는 fail-closed |
| 근거 선택·교정·최종 주장 | 인간 책임 |

같은 입력의 핵심 판정이 반복 실행에서 흔들리지 않는가 / 모델 실패 시 fallback이 있는가 / **AI 없이도 제품의 핵심 차별성과 비즈니스 이유를 설명할 수 있는가** / 만든 로직을 자기 말로 설명할 수 있는가.

## Gate 5 — Hypothesis-Proving Slice

첫 구현 목표는 기능 수가 아니라 **한 개 완결 slice**다. 실제 입력 → 핵심 메커니즘 실행 → 약속한 출력 → 그 결과가 문제 가설을 증명 → 최소 비즈니스 결과를 읽을 수 있음 → 이상 입력 1개 이상이 fail-closed 또는 설명 가능한 결과로 끝남 → README 약속과 실제 동작 일치.

> **Feature-freeze: 위가 통과하기 전 신규 기능 추가 금지.** 통과 시 `SLICE_READY`.

## Gate 6 — Reproducibility & Claim Parity

새 폴더/깨끗한 환경 설치·실행 / 누락 파일·로컬 절대경로·숨은 환경변수 0 / 한 명령 또는 명확한 최소 절차로 재현 / 동일 입력 2회 이상 실행해 핵심 판정 일치 / 대표 이상 입력 시험 / 처음부터 끝까지 실행 기록 / README·제출 답변·영상·발표의 각 주장을 코드·live proof와 대조 / sample·mock 값에 라벨 / exact SHA 기록 / **제출 패키지와 검사한 패키지가 hash 기준 동일**.
**통과 기준: critical claim parity 100% · critical source validity 100% · core fresh-run PASS.** 실패 시 `SUBMISSION_READY` 금지.

## Gate 7 — Honesty & Failure Ledger

사실·가설·미구현·미정·데모를 구분 / 정확도·시장 규모·비용 절감을 근거 없이 단정하지 않음 / 알려진 실패와 해결·미해결 상태 기재 / 과장 문구 제거 / 자동화 금지·인간 인계 조건 기재 / **기술 PASS가 사용자 가치·수상을 증명한다고 쓰지 않음**.

> 정직한 한계는 감점 방어 문구가 아니라 **신뢰 증거**다. (집계에서 본선 진출자 최고 평균 축.)

## Gate 8 — Business Legibility

누가 돈·시간·위험을 부담하는가 / 현재 방식의 비용·손실 단위 / 제품 행동이 전환·매출·공헌이익·회수·비용·위험·처리시간 중 하나로 이어지는가 / **sponsor가 내일 어디에 붙여 쓸지** 설명되는가 / 시장 크기는 근거 있는 범위 또는 `unknown` / 기존 대안·수작업·경쟁 제품과 비교 / AI·API 비용과 운영 책임을 숨기지 않음.
**실패 시 기술 설명을 늘리지 말고 비즈니스 계약을 좁힌다.**

## Gate 9 — Pitch & Q&A

실제 대회의 발표 제한 시간을 최신 권위로 사용한다(AX 본선 = 5분 + 질의).

첫 문장에 사용자·병목·결과 / as-is·to-be 대비가 한 화면 / 문제→근거→가설→데모→비즈니스→한계 순서가 끊기지 않음 / live demo가 핵심 가설을 보여줌 / **live 실패 시 짧은 녹화·스크린샷·trace fallback** / 제한 시간 안 최소 2회 연속 완주 / 대본 없이 핵심 로직·근거·한계 설명 가능.

Q&A 준비: 왜 이 문제인가 · 얼마나 자주·크게 발생하는가 · 왜 지금 방식은 실패하는가 · 왜 AI가 필요한가 · **AI가 틀리면 어떻게 되는가** · 어떤 지표가 좋아지는가 · 실제 도입에 무엇이 더 필요한가 · 무엇을 아직 검증하지 못했는가.
통과 시 `PITCH_READY`.

## 시간 배분 가드

- 문제·근거 Gate가 끝나기 전에 **구현으로 도피하지 않는다.**
- 핵심 slice가 통과하지 않으면 기능을 늘리지 않는다.
- **발표와 Q&A는 첫 slice 시점부터 병행한다** — 마지막 포장이 아니다.
- 검증을 무한 반복하지 않는다. blocker를 바꾸는 한 번의 비례 검증 후 다음 병목으로.
- 마지막 날에는 새 기능보다 claim parity·fresh run·발표 재현을 우선한다.

```text

[Status] BLOCKED | READY

```

## 작가 적용 — 다음에 먼저 감시할 것

집계는 개인 심사표가 아니므로 아래는 **과거 탈락 원인 단정이 아니라 다음 대회용 위험 가설**이다.

**이미 강한 부분**: 결정론 하네스·검증 계약 · 테스트/SHA/live evidence/submission receipt · 사실·가설·승인 상태 분리 · AI와 검증 로직 역할 분리. → 즉 Gate 4·6·7은 작가 홈그라운드다.

**먼저 감시할 부분**:
1. 큰 OS·세계관·하네스 비전이 **한 문장 병목보다 먼저** 나오지 않는가 (Gate 1)
2. 증거가 기술 품질에 몰리고 **실제 사용자 문제의 빈도·비용 근거**는 약하지 않은가 (Gate 2)
3. 기능은 여럿인데 핵심 가설을 증명하는 **1개 end-to-end slice가 늦지** 않은가 (Gate 5)
4. 안전·출처·아키텍처 설명이 **사용자 효용과 기업 경제성을 덮지** 않는가 (Gate 8)
5. 발표를 마지막 포장으로 미뤄 **5분 안에 읽히는 제품 구조**가 아닌가 (Gate 9)

## ⭐ 첫 적용 대상 — Cofathon 2026 (본선 07-30, KRAFTON FDE)

> 전략 SSOT = `applications/cofathon-2026/strategy.md` · 지참 하네스 = `applications/cofathon-2026/harness/`. **그쪽이 정본, 본 절은 Gate 매핑만 제공한다.**

Cofathon의 Cofa-Probe 는 **산출물이 아니라 *과정*을 채점**한다. 본 Gate와 축이 거의 그대로 겹친다 — 우연이 아니라, 두 대회가 같은 것(판정 가능성)을 보고 있기 때문이다.

> ⚠️ **아래 표는 보도자료 4축(A-4축) 기준이다. 채점 정본은 3축 12기준**(기술 관리·의도 관리·인지 관리 + 세부신호 ~40) — 실측 원문 cofa-probe-rubric §3. 매핑 자체는 유효하나 **판정은 항상 정본 기준**으로 한다. (2026-07-25 `strategy-axis-framing-stale` 패치 연쇄 반영.)

| Cofa-Probe 축 (A-4축, 구 프레이밍) | 대응 Gate | AX 집계가 주는 보강 |
|---|---|---|
| ① 문제 정의 과정 | **Gate 0 + Gate 1** | 판정 사유 최빈어 `병목` 2,391회. "API 붙인다"는 할 일, "정산 수치가 안 맞아 사람이 대조한다"가 문제 |
| ② AI 활용 방식 | **Gate 4** ★ | **AI 활용 점수는 상위권 차이가 가장 작았다** — 많이 쓴 게 아니라 *어디에 썼고 통제되는가*. 판정·계산은 결정론 코드로 |
| ③ 반복적 개선 과정 | **Gate 5 + §시간배분 가드** | feature-freeze. 핵심 slice 통과 전 기능 추가 금지 |

**시간 제약 반영**: 실질 빌드 **4시간 40분**(11:30~16:10).

> Gate 0 중 **공개된 부분**(공고·일정·루브릭·제출 구조)은 대회 전에 잠근다. **Gate 1·2는 과제가 당일 공개되므로 원리상 사전 잠금이 불가능하다** — 11:30~12:45(P0~P1)가 그 자리다. 사전 잠금의 효용은 **현장 시간을 문제 정의에 몰아주는 것**이지 파국 방지가 아니다.
> **리스크 등급**: 최고 위험은 **16:10 미제출**과 **토큰 소진** 둘뿐이다(회복 경로 없음). 문제 정의 오류·증거 부족은 **보통** — 비용이 빌드 시간으로 청구될 뿐, Feature-freeze와 15:10 수렴 게이트가 받아낸다.

16:10 제출 후 **17:00 블라인드 리포트 기반 공개 토론**이 수상을 가르므로, Gate 9(Pitch & Q&A)는 발표가 아니라 **토론 방어**로 변형해 준비한다 — Q&A 8문항이 그대로 쓰인다.

**NO RULE 조항**(지참 하네스 허용)과의 관계: 본 Gate 자체가 지참 가능한 자산이다. 단 **파일럿 0회**이므로 현장에서 처음 돌리는 부담을 감안해, 대회 전 Gate 0~2 만이라도 미리 한 번 통과시켜 두는 편이 안전하다.

## 냉정 (과신 가드)

- 이 자료는 **개별 참가자 심사평이 아니다.** 작가의 실제 탈락 사유를 특정할 수 없다.
- 집계 수치·단어 빈도를 독립 재계산하지 못했다 — 전부 `organizer_reported`.
- 6개 기업·**한 대회** 결과이며 다른 대회의 루브릭을 대체하지 않는다.
- 한 기업의 `51% / 40%`(매출·공헌이익 관점 / 발표 명료성)를 전체 기업 평균으로 일반화하지 않는다.
- 심사 가능성을 높이는 계약이지 **수상 보장이 아니다.**
- 예선 AI 채점 방식의 공정성·타당성은 확정되지 않았다.
